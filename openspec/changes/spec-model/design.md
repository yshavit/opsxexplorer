## Context

See proposal.md — Why. Existing pieces this builds on:

- `src/vfs/` — `Fs<'a>` is a read-only view (`read`, `list_dir`, `exists`) over either the live working tree (`Workspace::current()`) or a resolved commit (`Workspace::at(&GitRef)`). Both borrow `&'a Workspace`, so two views can be held at once.
- `src/changes/` — `Changes::resolve(&Change) -> ChangeView` pairs a change with its `DiffBase`; `Changes::open(&ChangeView) -> Fs` opens **the diff base**. `Changes.vfs: Workspace` is private and `Workspace::current()` is unreachable from outside the crate's `changes` module, so there is currently no way to read a change's own delta specs for an archived change — its diff base is the commit *before* the change directory existed.
- `pulldown-cmark` 0.13.4 and `similar` 3.1.2 are in `Cargo.toml` and unused. `similar` belongs to change 2; `pulldown-cmark` is a transitive dependency of `tui-markdown` regardless and belongs to change 3. This change adds `mdq` 0.10.
- Facts established by surveying the repo's real spec files: no `spec.md` anywhere contains a fenced code block (fences appear only in `design.md`, which this change does not read); 57 of 57 prose paragraphs sit on a single unwrapped line, median longest line 110 characters and max 472; every one of the 49 requirements has intro text.

## Goals / Non-Goals

**Goals:**

- One parsed shape shared by a spec of record and a delta spec, so change 2 joins them without special-casing which side it holds.
- Body text that loses no authored content and is normalised **identically on both sides**, so an unedited requirement compares equal and produces no diff. Byte-identity with the source is explicitly not a goal (see Decisions).
- A parser boundary narrow enough that swapping the markdown library later touches one file and no consumer.
- Owned model values with no lifetime tie to the `Fs` they were read through, so the TUI can hold parsed specs across frames.
- The `change-model` addition adds *reach* without weakening "Resolved diff base travels with its change" — the two views stay a pair, never handed out separately.

**Non-Goals:**

- Rendering the model, or any styling decision about it (change 3).
- Any join, match, or comparison between the two sides (change 2). This change loads both sides and validates only the one cross-side condition the spec names: a MODIFIED/REMOVED entry with no base spec at all.
- Reading `proposal.md` / `design.md` / `tasks.md`, or parsing anything below the scenario-body level (bullet structure, WHEN/THEN roles). Bodies are text.

## Decisions

**Parse with `mdq`'s `md_elem`, not by hand.** `MdDoc::parse(text, &ParseOptions::gfm()) -> Result<MdDoc, InvalidMd>` yields `MdElem::Section { depth: u8, title: Vec<Inline>, body: Vec<MdElem> }`, and — this is why it wins — sections are genuinely **hierarchical**: a `##` section's body contains the `###` sections, whose bodies contain the `####` sections. That is exactly the OpenSpec shape, so `Requirements → Requirement → Scenario` falls out of the tree instead of being reconstructed. A requirement's intro is the elements in its section body before the first depth-4 subsection; its scenarios are those subsections. No grouping fold, no depth bookkeeping, no boundary arithmetic.

Rejected: **hand-rolled line scanning** (the previous draft of this design). Its stated appeal was that OpenSpec's grammar is only four fixed heading prefixes, so a scanner is a direct transcription of it and makes byte-exact body capture trivial. That reasoning had a hole. A heading-shaped line inside a fenced code block — or an indented code block, an HTML block, or a blockquote — is not a heading, and a prefix match cannot tell. The previous draft waved this away on the evidence that no `spec.md` *in this repo* contains a fence. But opsxexplorer browses **any** local OpenSpec repo; this repo is merely the validation data, and specs elsewhere routinely fence example payloads (OpenSpec's own artifact instructions embed fenced markdown examples). That makes the gap a first-contact-with-another-repo bug, not a deferred risk. The draft also argued that a parser "only supplies heading boundaries," as though that were a small contribution — it inverts the value, since boundaries are the entire hard part and the bodies are deliberately not interpreted at all.

Rejected: **`markdown` 1.0 (mdast) directly.** `to_mdast` gives correct boundaries *and* keeps `position: Option<Position>` with byte `offset`s on every node, so bodies could be sliced byte-exact out of the source. It is the only option that preserves both correctness and byte-exactness. Rejected because byte-exactness is not a requirement we hold (see the next decision) and mdast's headings are flat siblings, so the Requirement/Scenario nesting would have to be rebuilt by hand — reintroducing, in milder form, the depth bookkeeping `md_elem` removes. `mdq` is itself built on `markdown`, so this stays the obvious fallback if byte-exactness ever becomes load-bearing.

Rejected: **`pulldown-cmark`**, already in `Cargo.toml`. Correct boundaries, but the worst of both — a flat event stream with no nesting *and* normalised inline text, so recovering source means pairing events with `OffsetIter` ranges by hand. It stays in the tree for change 3 (`tui-markdown` depends on it regardless).

**Bodies are re-serialised markdown, not source slices — byte-exactness is explicitly not a goal.** `md_elem` discards source positions during construction (mdast's `position` is consumed internally and not surfaced on `Section`/`Paragraph`), so the only way back to text is `mdq::output::MdWriter::write(&ctx, &nodes, &mut out)`. Bodies are therefore mdq's rendering of the parsed tree: semantically equal to the source, cosmetically normalised (bullet markers, emphasis characters, escaping may be rewritten).

This is a deliberate relaxation of the exploration brief, which called for byte-faithful bodies. Yuval's call, and the reasoning holds: what actually matters is that no authored content is lost and that **both sides get identical treatment**, so an unchanged requirement compares equal and produces no diff. Byte-exactness is a stronger property than either consumer needs — change 2 diffs the two sides against each other, not against the file, and change 3 renders through `tui-markdown`, which re-renders anyway. The residual cost is that the TUI shows mdq's markdown rather than the file's own bytes; if that turns out to matter, `markdown`/mdast (above) swaps in behind an unchanged model.

Two writer options are load-bearing and must be set explicitly: `text_width: None` (any wrapping value would re-flow prose and wreck line-level diffs) and `include_thematic_breaks: false` (it would inject `-----` separators that exist in no source file).

**The model stays plain `String`s — no `mdq` types cross the module boundary.** `Requirement`/`Scenario`/`Delta` hold owned `String`s, and `mdq` appears only inside `src/specs/parse.rs`. This is what makes the swap above cheap: replacing the parser touches one file and no consumer, because nothing downstream ever sees an `MdElem`. Alternative considered: store `Vec<MdElem>` and let change 3 render from the tree. Rejected — `tui-markdown` takes `&str` and `similar` diffs text, so both consumers would immediately serialise anyway, and the model would have leaked a dependency for nothing.

Owned `String`, not borrowed `&'a str`, for the reason it always was: the parsed model outlives the `Fs` it was read through, and borrowing would push a lifetime through `App`.

**Intro is a plain `String`; an "absent" intro and an "empty" one are the same thing, because a spec file cannot say otherwise.** `Requirement { name: String, intro: String, scenarios: Vec<Scenario> }`.

An earlier draft made this `Option<String>`, with `None` for a requirement supplying no intro block and `Some("")` for one supplying an empty block — carried over from the exploration brief, which asserted the two must stay distinguishable. They cannot be, and the draft was wrong to claim they were. The only textual difference between the two is whether a blank line follows the requirement heading, which is conventional markdown formatting carrying no authorial intent. Parsing to a tree settles it structurally: blank lines are not elements, so "no intro" and "a blank intro" both arrive as a section body with zero elements before the first depth-4 subsection. There is no second state to represent. Empirically neither shape occurs anyway: across all 49 requirements in this repo's main specs and archived deltas, every single one has real intro text.

The underlying principle, which the brief's scenario-subset point *does* respect: **absence is observable only for things that have identity.** A requirement is named, so "not mentioned in this delta" is observable and load-bearing. A scenario is named, so a MODIFIED entry listing three of the base's five scenarios genuinely leaves two unmentioned — that distinction is real and is preserved. An intro block has no name; it is just the region between a heading and the first scenario. There is no mention of it that could be absent, so the brief's intro rule was an over-generalisation of the valid scenario rule.

What survives is a real question, but not a parsing one: when a MODIFIED entry's intro is empty and the base's is not, does that mean "unchanged, defer to the base" or "the intro was deleted"? That is an interpretation policy, and it belongs to change 2 — not smuggled into the parser as a distinction the source never drew. **Change 2's brief has already settled it:** an empty intro yields an `Unmentioned` intro and the base's is shown as context, under its general rule that absence in a delta means unmentioned rather than deleted (`notes/spec-diff/02-spec-diff.md`). The consequence — that deliberately emptying an intro is therefore inexpressible, not merely ambiguous — is recorded there. `spec-model` reports only what the file says: the intro is empty.

**No trailing-blank-line rule, and no blank-line handling at all.** An earlier draft needed one: when bodies were source slices running from one heading to the next, the last block in a file ended at EOF instead of at a heading, so how many trailing newlines it carried depended on its position in the file rather than its content — which would have produced phantom diff lines. Parsing to a tree deletes the problem outright. Blank lines are not elements, so a section body simply does not contain them, and every block is bounded identically regardless of where it sits. One fewer rule to state, justify, and guard with a test — an instance of the general simplification that motivated using a real parser.

**Soft line breaks inside a paragraph are normalised away, and that is fine here.** A soft-wrapped paragraph parses to one `Paragraph` element and re-serialises as a single unwrapped line (given `text_width: None`). This is a genuine change from the previous draft, which preserved source newlines. It is safe because both sides are normalised identically, so a paragraph that was not edited still compares equal — and it is arguably better, since a change to a hard-wrapped paragraph no longer cascades reflow noise into the diff. Independently measured on this repo: 57 of 57 prose paragraphs are already single unwrapped lines with no soft wrapping anywhere, so nothing observable changes today.

**Renames are a separate list, not a requirement variant.** `Delta { purpose: Option<String>, entries: Vec<DeltaEntry>, renames: Vec<Rename> }`, where `DeltaEntry { op: DeltaOp, requirement: Requirement }`, `DeltaOp` is `Added | Modified | Removed`, and `Rename { from: String, to: String }`.

A RENAMED entry is shaped differently from the other three: it is a pair of names in a bullet list, with no heading of its own and no body. Folding it into `DeltaEntry` would mean a `Requirement` whose `intro`, `scenarios`, and even `name` are meaningless for that variant, and every consumer would carry a match arm to skip it. Keeping it a separate field means `entries` is uniformly "a requirement named by this delta" and renames are consulted only by the code that cares about them.

REMOVED *is* a `DeltaEntry`, with an empty `intro` and `scenarios: []`, because a removal genuinely is a requirement identified by name — the name is the join key, and the body is recovered from the base. That is the same shape as any other entry, just empty, so it needs no special variant.

**`Changes` gains `views(&ChangeView) -> Result<ChangeViews<'_>, FsError>` returning both `Fs` values as one value — not a bare `current()`.** `ChangeViews { live: Fs<'a>, base: Fs<'a> }`, where `live` is always `Workspace::current()` and `base` is `Current`/`At(r)` per the change's already-resolved `DiffBase`.

A bare `pub fn current(&self) -> Fs<'_>` would be one line and would technically unblock the loader. Rejected: it hands out a view with no association to any change, so a caller can pair the live view of one change with the base view of another, or forget to resolve at all. The existing "Resolved diff base travels with its change" requirement exists specifically so consumers never re-derive this pairing; a free-floating `current()` reintroduces exactly the re-derivation that requirement forbids, one level up. Returning the pair keyed off a `ChangeView` extends that invariant to both sides instead of poking a hole in it.

Alternative considered: a capability-aware accessor on `Changes` returning the two `spec.md` contents (or the two parsed specs) directly for a `(change, capability)`. Rejected on ownership of knowledge: `change-model`'s job is changes and diff bases, and it has no business knowing that specs live at `openspec/specs/<cap>/spec.md` and `<change>/specs/<cap>/spec.md`. `spec-model` must own the spec-of-record path regardless, so putting the delta path in `change-model` splits one layout convention across two capabilities where it would drift. `views` is the narrowest thing that closes the gap.

`open(&ChangeView)` is kept, unchanged, for the existing base-only callers and their tests; it and `views` resolve the base through one shared private helper so the two cannot drift.

**Loading is per-capability, and enumeration is separate from loading.** Two operations: `capabilities(&ChangeViews) -> Result<Vec<String>, FsError>`, which `list_dir`s `<change>/specs/` on the **live** view and returns directory names sorted alphabetically; and `load(&ChangeViews, &str) -> Result<SpecPair, SpecError>` for one capability, where `SpecPair { delta: Delta, base: Option<Spec> }`.

This grain is what makes "a failure affecting one capability does not prevent loading the others" true by construction rather than by a partial-results type: each capability is a separate call and a separate `Result`, so a malformed delta in one is an `Err` the caller renders in that capability's tab while every other call still succeeds. Alternative considered: `load_all(&ChangeViews) -> Vec<(String, Result<SpecPair, SpecError>)>`. Rejected — it builds the isolation structure the caller would have built anyway, and change 3 renders capabilities as tabs and will want to parse the selected one lazily rather than every one up front.

`list_dir` on a missing `<change>/specs/` returns `FsError::NotFound`, which `capabilities` maps to an empty `Vec` — a proposal-only change is "no spec changes", not an error, per spec. Only `NotFound` is absorbed; every other `FsError` propagates, so a genuine read failure is not silently reported as an empty change.

**`base: Option<Spec>` — absence is a value, and the MODIFIED/REMOVED-without-base check happens at load time.** A change introducing a brand-new capability has no base file at the diff base at all (real case: `2026-08-07-tui-initial` introduces both `tui` and `tui-changelist`), so `None` must be an ordinary success. But an entry that *needs* a base and has none is an authoring error worth naming, so after parsing the delta the loader checks: if `base.is_none()` and any entry's op is `Modified` or `Removed`, return a distinct error carrying the capability and the offending requirement name.

Alternative considered: defer the check to change 2, which will be doing the requirement-level join anyway and will independently notice a MODIFIED with no counterpart. Rejected — change 2's "no counterpart" case is about one requirement missing from a base that exists, which is a genuinely different (and possibly more forgiving) situation than the whole spec of record being absent; conflating them would make the two indistinguishable to the UI. Catching the whole-file case where the file is opened keeps each layer reporting what it is actually in a position to know.

**Errors: a new `SpecError` locating failures structurally, not by line number.** Variants: `Structure { path, at: Location, kind: StructureErrorKind }` with `kind` covering the three named malformed cases (scenario before any requirement, unrecognised `## <OP> Requirements`, rename missing its `TO:`); `Markdown { path, source: InvalidMd }` wrapping an mdq parse failure; `MissingSpecDocument { capability }` for an enumerated capability directory with no `spec.md`; `MissingBaseSpec { capability, requirement }` for the case above; and `Fs(FsError)`. House pattern throughout — a plain enum with hand-written `Display`, `Error::source`, and `From` conversions, no `thiserror`, matching `src/vfs/error.rs` and `src/changes/error.rs`.

**Line numbers are not available, and this is a real cost of the parser choice worth stating rather than glossing.** An earlier draft promised a 1-based source line on every parse error, on the grounds that a line scanner has one for free. `md_elem` does not: it drops mdast's positions when building its tree, and `InvalidMd` carries no position either — its `MarkdownPart` wraps an mdast node whose documented use is "`Debug` it". So `Location` is structural: the operation section and, where known, the requirement name (e.g. *under `## MODIFIED Requirements`, requirement "Change discovery"*). The spec asks the error to say *where*, and a structural address satisfies that — arguably better for a TUI that is displaying a rendered requirement rather than a text buffer with a cursor. Recovering true line numbers is possible if it ever matters, but only by switching to `markdown`/mdast, which retains them.

Parsing fails on the first malformed construct rather than accumulating a list: the UI shows one capability's error in one pane, and an authoring mistake this structural is usually corrected and re-read immediately.

**Module layout: `src/specs/`**, sibling to `src/vfs/` and `src/changes/`, with `model.rs` (the shapes), `parse.rs` (the `mdq` tree walk — the only file that mentions `mdq`), `load.rs` (the two operations above), and `error.rs`. Plural directory name matching the existing `changes`/`vfs` convention, even though the capability is `spec-model` — `changes` is likewise the module for `change-model`.

**Tests parse the repo's own real spec files, not only synthetic ones.** Four archived changes cover `## Purpose`-then-ADDED, multi-capability ADDED with no base, and ADDED+MODIFIED with no `## Purpose`. Neither REMOVED nor RENAMED exists anywhere in this repo, so those two paths — and every malformed-input case — need synthetic fixtures built with the `TempDir` / `write_file` / `stage_and_commit` helpers already in `src/changes/mod.rs::test_support` and `src/vfs/mod.rs::test_support`. Reading the live repo's files in a test that must also exercise archived diff bases means the git-history-dependent tests stay synthetic; the real-file tests are pure parser tests against `openspec/**` read from disk.

## Risks / Trade-offs

- [A heading-shaped line inside a fenced code block, indented code block, HTML block, or blockquote is misparsed as a real heading] → **Resolved by design.** This was the previous draft's headline deferred risk, and delegating to a CommonMark parser removes it entirely rather than mitigating it. It is the main reason the hand-rolled scanner was abandoned: opsxexplorer reads arbitrary OpenSpec repos, and specs elsewhere fence example payloads routinely. Guarded by a test whose fixture puts `### Requirement: Not Real` inside a fence and asserts it does not become a requirement.
- [Bodies are mdq's re-serialisation, so what the TUI shows is not byte-identical to the file — bullet markers, emphasis characters and escaping may be rewritten] → **Knowingly accepted**, as a deliberate relaxation of the brief's byte-faithfulness rule. Both sides are normalised identically, so diffs stay clean and unchanged requirements compare equal; the exposure is purely cosmetic drift between the pane and the file. Two concrete guards: `text_width: None` and `include_thematic_breaks: false` must be set, since either default would corrupt output structurally rather than cosmetically. The escape hatch is real and cheap — `markdown`/mdast slices byte-exact bodies out of the source and swaps in behind an unchanged model, because no `mdq` type crosses the module boundary.
- [This entire design was derived by reading `mdq`'s source, never by compiling against it — in particular, what its re-serialisation does to these specific files is unverified] → **Mitigated by making it the first implementation step, with a hard stop.** Task 4.0 is a round-trip spike over two real spec files, and its acceptance criterion is idempotence rather than fidelity to the file, since idempotence is exactly what makes "both sides normalised identically" true. Task 4.0a requires that a failure stops the work and escalates rather than being worked around with a post-processing fixup — because a failure means the parser choice needs revisiting, which is a design decision. The fallback is already specified (`markdown`/mdast, above), so the escalation has somewhere to go.
- [`mdq` has no feature flags, so it pulls its CLI and query-language machinery into a TUI binary that uses neither] → **Knowingly accepted; measured, not estimated.** `cargo tree` puts it at roughly 32 additional transitive crates over the current dependency set — `clap` 4 with derive and the `anstream`/`anstyle` family behind it, `pest` + `pest_derive` for the query grammar, `derive_builder` + `darling`, `fancy-regex`, `toml`, `serde_json`. All of it is unconditional: `mdq`'s manifest declares no `[features]` and marks nothing optional, and we use only `md_elem` and `output`. For comparison, `markdown` alone adds 3. The cost is build time and binary size for a local developer tool — not correctness, not runtime, and not a maintenance burden, since none of it is in our code. Recorded because it was not part of the information available when the parser was chosen, and because it is the one argument that would favour the `markdown`/mdast fallback on grounds other than byte-exactness.
- [Parse errors cannot report a line number] → **Knowingly accepted**, forced by `md_elem` dropping positions. Errors locate failures structurally instead (section + requirement name). Acceptable for a TUI that displays rendered requirements rather than a text buffer; the fix, if it is ever wanted, is the same mdast swap.
- [Change 2 must not diff these bodies at line granularity] → **Deferred to change 2, deliberately, but recorded here so it is not rediscovered late.** Re-serialising with `text_width: None` emits one line per paragraph, which matches how these files are already authored: measured across all 9 spec files, 57 of 57 prose paragraphs occupy a single unwrapped line, median longest line 110 characters and max 472. A line-granularity diff therefore marks an entire 472-character paragraph changed when one word was edited — useless, and guaranteed rather than hypothetical. The fix is granularity, not normalisation: `similar` is already reserved for change 2, and `TextDiff::from_lines(..).iter_inline_changes(..)` refines to word level within changed lines, with `from_words` over the whole block as the alternative. Nothing about it changes this change's model.
- [`ChangeViews` holds two `Fs<'a>` borrowed from the same `&'a Workspace`, one of which may be a `GitTreeFs` borrowing the repo] → **Resolved by design.** Both are shared borrows of `&'a self`, so holding them simultaneously is fine; `Fs` is read-only with no interior mutability. Nothing here needs `RefCell` or cloning the repo handle.
- [Adding `views` alongside `open` gives `Changes` two overlapping accessors] → Accepted, small. `open` has existing callers and tests and encodes the base-only intent that most of `change-model`'s current spec is about. Both resolve the base through one private helper, so the duplication is in the signature only, not the logic.
- [Failing the whole parse on the first malformed construct means an author fixing three mistakes recompiles the view three times] → Accepted. Batch-collecting errors needs a partial model or an error-list type threaded through every layer, for a workflow (hand-editing a spec into validity) that is already iterative. Revisit only if real specs turn out to be malformed in bulk.
- [`capabilities` reads the live working tree even for an archived change, so a capability directory deleted after archiving would not be enumerated] → Accepted and correct. The delta specs of an archived change are read from the working tree by definition (that is the whole asymmetry this change exists to expose); if the directory is gone from the working tree, there is no delta to show. The base side is unaffected and still reads at the resolved diff base.
