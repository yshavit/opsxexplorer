## Context

`App` (`src/tui/app.rs`) owns all key routing today: `handle_key` dispatches to `handle_left_key`/`handle_right_key` based on `Focus`, both of which mutate pane-local state (`list_state`/`h_scroll` on the left, `cursor`/`expanded`/`tab` on the right). `q` is intercepted earlier still, in `mod.rs`'s `event_loop`, before `App::handle_key` ever runs.

The left pane's `h_scroll` is a direct precedent for this change's scrolling model: a plain accumulated offset, clamped each render against a `max_h_scroll` the renderer computes and caches back onto `App` (`set_max_h_scroll`). This is distinct from the right pane's `cursor`, which addresses a *selectable row* in a flattened tree — a model that has a real limitation: if the first row in the flattened list isn't itself selectable (e.g. a group heading), the top of the content can become unreachable by scrolling, since the cursor can never land above the first selectable row. This change deliberately uses the `h_scroll` shape for the modal, not the `cursor` shape, so the modal doesn't inherit that limitation. The right pane's own scrolling is unchanged by this decision — the same limitation exists there but is out of scope for this change.

## Goals / Non-Goals

**Goals:**
- Keep the modal's state cleanly separate from pane state, so that closing it restores the panes to exactly the state they were in when it opened, as a structural guarantee rather than something each key handler has to preserve by convention.
- Line-by-line scrolling of fully static content, so the entire content — including its very first line — is always reachable, regardless of viewport height.
- A popup whose width never changes, regardless of scroll position: the content and its width are both computed once, up front, not per frame from whatever happens to be currently visible.

**Non-Goals:**
- Mouse support.
- Collapsible sections. An earlier iteration of this change made the Left pane and Right pane sections independently collapsible, with their own selectable headers and a cursor that moved between them. That added real complexity (disclosure state, a header-only cursor, scroll-to-reveal on expand) for content that's short enough to just show in full and scroll through — it was simplified away in favor of always-full content and plain line scrolling.
- Deriving the modal's key/description text from the actual key-match arms in `handle_left_key`/`handle_right_key`. The content is static (see Decision 2).

## Decisions

**1. The modal is a separate field on `App`, not a third `Focus` variant.**
`Focus` currently answers "which pane's own persistent state should this key affect?" Adding `Focus::Help` would conflate that with "is the overlay showing," forcing every existing `Focus::Left`/`Focus::Right` match arm to account for a case that doesn't apply to it, and would make "closing the modal returns exactly to prior pane state" an emergent property instead of a guaranteed one. Instead, `App` gets its own modal-state field, and `handle_key` checks it first, short-circuiting to modal-specific handling before the existing `match self.focus`. `focus` itself is never read or written by opening/closing the modal.

This state/rendering separation extends to coloring too (see Decision 4): `focus` still names which pane *would* be focused, and each pane's own diff/selection state is untouched, but what gets rendered now also depends on whether the modal is open. No pane-level state changes; only what the rendering functions do with it.

**2. The keybinding list itself is a static table, not derived from the key-handling code.**
`handle_left_key`/`handle_right_key`'s match arms have no machine-readable description today, and building that infrastructure is out of scope for this change. The content is hardcoded (`src/tui/help.rs`) alongside the sections it documents.
*Trade-off accepted:* the static table can drift from actual behavior if the match arms change later without the table being updated (see Risks).

**3. The modal's content is a fixed, precomputed list of lines — not a per-frame-flattened row tree.**
Since nothing in the modal expands or collapses, its content (`help::lines()`) is the same every time it's asked for: a plain function of the static tables, with no state input. Scrolling moves a `help_line_offset` over this fixed list, clamped each render against a cached `help_max_line_offset` — exactly the left pane's `h_scroll`/`max_h_scroll` shape, reused for the same reason: a plain offset over static content can always reach line 0, unlike a cursor that's only ever allowed to land on a selectable row (see Context).
*Alternative considered:* keep the earlier per-frame-flattened-row-tree approach (mirroring `diff_row::flatten`) that supported collapsible sections. Rejected along with collapsibility itself (see Non-Goals) — once the content stops varying, flattening it fresh every frame is pure overhead, and the cursor-based navigation it existed to support is gone.

**4. Popup sizing computes content height and width directly, then clamps to the frame; content is padded on each side; the border has no shadow.**
Unlike the right pane's wrapped prose, the modal's lines are short and fixed-format (`key   description`), so their count and the longest line's width don't depend on rendering width the way wrapped text does — both can be computed straightforwardly, once, from the static content (`help::lines()`). Because the content never varies, this width is also fixed: it does not change as the user scrolls. Height is clamped to the current frame's height (minus a small margin); width is clamped the same way, though in practice the content is short enough that this rarely engages. The popup renders via a `Clear` + bordered widget with `Padding::horizontal(H_PADDING)` (currently 2 columns) on its left and right, matching the conventional ratatui popup approach. This is the one genuinely new rendering mechanism the change introduces — the two main panes never overlay each other today, so there's no existing "popup over other content" precedent in `mod.rs`'s `render`.

*Bug found and fixed during review:* `Padding::horizontal(n)` sets `n` columns on **both** the left and right edges (`2n` total), but the width computation that sizes the popup originally added the padding constant only once. This silently undersized the popup by exactly the padding amount, clipping the tail of whichever line happened to be widest (observed as `"...selected r"` instead of `"...selected row"`). The fix makes `H_PADDING` the single value both call sites read — the `Padding::horizontal(H_PADDING)` call and the `+ H_PADDING * 2` in the width computation — so the two can no longer drift apart, and added a regression test (`widest_entry_line_is_not_clipped_by_the_popups_own_padding`) that renders the modal end-to-end and asserts the widest line appears in full.

The popup's own border uses a visual treatment distinct from the two panes' plain bordered blocks — currently a light-blue background (`on_light_blue`), a dark-gray rounded border, and section headings rendered bold and underlined rather than colored. (An earlier iteration used a magenta border and magenta headings; the named ANSI `Color::Magenta` rendered as black in at least one real terminal, evidently due to palette remapping in that terminal's color theme — bold was chosen instead specifically because it doesn't depend on how a terminal maps the 16 named colors.) An earlier iteration also added a rendered drop shadow (`Block::shadow`); it read poorly in practice at small terminal sizes and was removed. The spec (`specs/tui-help/spec.md`) only requires that the modal be "visually distinct" and doesn't pin these specifics, so this choice can change again without a spec change.

**6. The right pane's vertical scrollbar now hides when there's nothing to scroll, rather than rendering in an empty state — a change to an existing capability, made in passing.**
`render_right_scrollbar` is shared by the right pane's diff view and the help modal. While tuning the modal's own scrollbar, the same "hide when there's nothing to scroll" behavior was applied to the shared function, which also changes the right pane's long-standing "always show the scrollbar, even in a nothing-to-scroll state" convention (`tui-specdiff`'s "The right pane scrolls vertically and indicates its scroll position" requirement, now updated as a `MODIFIED Requirement` in this change's delta specs). This is called out explicitly because it's easy to miss: the change originated from a request about the modal, not the right pane, but the two share code.
*Alternative considered:* give the modal its own scrollbar-rendering function so the right pane's convention would be untouched. Rejected as unnecessary duplication for what is, on reflection, an improvement to both call sites — a static, permanently-empty scrollbar track was arguably never a good default.

**5. Dimming both panes while the modal is open is a single post-process pass over already-styled output, not a flag threaded through every styling function.**
Color in the two panes is produced by many separate call sites — `layout::operation_style`, the word-level diff insertion/deletion highlighting, the dimmed-unmentioned and dimmed-date treatments, the group-heading box borders, and the focus border style. Threading a "no color" parameter through all of them would touch most of `layout.rs`, `diff_row.rs`, and large parts of `mod.rs`. Instead, both panes already funnel their fully-styled output through one place right before handing it to a ratatui widget — the `ListItem`s built in `render_left_pane`, the `Line`s built in `render_right_pane`, and the border `Block` each pane constructs. A single function strips every span's foreground (and background, where set) color down to one flat neutral tone, leaving non-color modifiers (bold, underline, reversed) untouched, and is applied at those spots whenever the modal is open.
*Alternative considered:* thread a "dimmed" flag through `layout::operation_style` and the other color-producing functions so each one renders its own neutral variant. Rejected — far more call sites to touch for the same visible result, and it would mean every future color addition also needs to remember to handle the dimmed case, where the post-process approach handles it automatically by construction.
*Trade-off:* this also flattens the *semantic* dimming already used for unmentioned pieces and archived dates into the same generic treatment as everything else while backgrounded (see Risks).

## Risks / Trade-offs

- **Static content can drift from real bindings** (Decision 2) → keep the table close to the match arms it documents; treat it as a required update whenever `handle_left_key`/`handle_right_key` change.
- **New popup rendering path** (Decision 4) → keep it narrowly scoped to this one modal (fixed `Clear` + bordered block) rather than building a general dialog abstraction, since it's the only overlay this app has.
- **Desaturating both panes collapses their semantic dimming** (unmentioned pieces, archived dates) into the same generic neutral treatment as everything else (Decision 5) → accepted: both panes are inert background while the modal is open, so the distinction they'd otherwise carry has no reader depending on it in that moment.
- **A third top-level field on `App`** alongside `focus` and the pane-specific state → gate it at the very top of `handle_key` so `handle_left_key`/`handle_right_key` stay completely unaware the modal exists, keeping the added surface area to one entry point.
- **The right pane's cursor-based scrolling keeps the same top-of-content limitation** the modal was specifically redesigned to avoid (see Context) → accepted as out of scope for this change; noted here so it isn't mistaken for an oversight.
- **Padding applied on both sides is easy to undercount once** (Decision 4) → the bug this caused is fixed by construction now (one constant, read by both the padding call and the width computation), but the general shape of the mistake — a widget's per-side setting silently doubling when computing an aggregate — is worth remembering elsewhere `Padding`/`Margin` are used.
- **The right pane's scrollbar convention changed as a side effect of a help-modal-focused change** (Decision 6) → `tui-specdiff`'s spec of record is updated via this change's `MODIFIED Requirement`, not left implicit; see proposal.md's "Modified Capabilities".
