## Context

See proposal.md - Why. The relevant existing pieces:

- `Spec.purpose: Option<String>` and `Delta.purpose: Option<String>` (`src/specs/model.rs:24,61`) are already parsed and correct; nothing here touches `spec-model`.
- `compare::changed_or_unchanged(base, delta) -> Piece` (`src/diff/compare.rs:49`) already implements exactly the comparison this change needs for purpose text: `Unchanged` when equal, `Replaced` when too dissimilar to interleave, `Changed` (with runs) otherwise. It's already used for a requirement's intro.
- `CapabilityDiff { capability, requirements, errors }` (`src/diff/model.rs`) is the type `diff()` returns and the only thing the TUI layer sees; it currently has no purpose field.
- The right pane is built in two stages (`tui-specdiff`'s own design.md): `CapabilityDiff` + collapse state → `Vec<DiffRow>` (`src/tui/diff_row.rs`), then `(DiffRow, width) → Vec<Line>` (`src/tui/layout.rs`, assembled by `build_diff_lines` in `src/tui/mod.rs`).
- `RowKey { capability: String, requirement: String, scenario: Option<String> }` identifies a row's collapse state in the `HashSet<RowKey>` `App` holds. Every existing row addresses a requirement (optionally a scenario within it); nothing today addresses a capability-level row with no requirement name.
- `group_heading_box(op: &Operation, width, count) -> Vec<Line>` (`src/tui/mod.rs:422`) draws the bordered "Added Requirements" / "Modified Requirements" style heading, degrading to a plain styled line when the pane is too narrow.
- `wrap_spans` (`src/tui/wrap.rs`) is the pane's only wrapping primitive today, and it is word-boundary-aware by design. The collapsed purpose row needs a second, deliberately dumber primitive: a literal character slice plus an ellipsis, indifferent to word boundaries, per the resolved conversation.
- `App` already caches a layout fact computed at render time for use by later key handling: `right_viewport_rows` (`src/tui/app.rs:73`), set by `set_right_viewport_rows` from `render_diff_tabs` (`src/tui/mod.rs:205`) each frame, and read back by `move_cursor`'s half-page handling. Whether the purpose row is collapsible at all is now also a render-time fact (it depends on the pane's current width), so it needs the same treatment.

## Goals / Non-Goals

**Goals:**
- Compute the purpose comparison once, in `spec-diff`, as a value `tui-specdiff` can render with no further judgement calls (it decides once whether there's anything to show at all).
- Reuse the existing `Piece`/comparison machinery and the existing heading-box/degrade behavior rather than inventing parallel versions for purpose.
- Keep the new truncation primitive isolated and trivial to test in isolation from wrapping.

**Non-Goals:**
- Any change to `spec-model`'s parsing, or to diff-base/git resolution.
- Rendering `proposal.md`/`design.md`/`tasks.md` content, or any left-pane change.
- Pixel/column-exact truncation for wide or combining characters — the char-count measure has the same known limitation the rest of the pane already accepts (see the original `tui-specdiff` design.md's Risks).

## Decisions

**`CapabilityDiff` gains `purpose: Option<Piece>`, populated only with `Piece::Added`, `Piece::Changed` or `Piece::Replaced`.** `diff()` computes it as: `None` if `pair.delta.purpose` is `None`; otherwise run `compare::changed_or_unchanged(base_purpose, delta_purpose)` (with `base_purpose` being `pair.base.and_then(|s| s.purpose).unwrap_or_default()`), and map its `Piece::Unchanged` result to `None`, passing everything else through unchanged. No new variant is added to `Piece` — `Unchanged`, `Deleted` and `Unmentioned` are simply never reachable through this path, the same way `Operation` has no "unmentioned" arm today (per the existing design.md's "different mappings on purpose" note). Alternative considered: a dedicated `PurposeComparison` enum with only three variants. Rejected — it would duplicate `Piece::Added`/`Changed`/`Replaced` field-for-field and the rendering code would need its own match arms instead of reusing `piece_spans`/`piece_marker`.

**`RowKey` becomes an enum: `RowKey::Purpose { capability }`, `RowKey::Requirement { capability, requirement }`, `RowKey::Scenario { capability, requirement, scenario }`.** The purpose row has no requirement name to hang off of, and a sentinel (empty string, or similar) in the existing struct would let an impossible state compile. Cost: every existing construction site (`diff_row.rs`, `app.rs`, and their tests) changes shape. This is mechanical — none of it changes behavior for the requirement/scenario cases — and is worth doing once rather than carrying a sentinel indefinitely. Alternative considered: keep the struct, add `requirement: Option<String>`. Rejected — `Scenario { scenario: Some(_) }` with `requirement: None` would then also compile and mean nothing.

**Whether the purpose row can collapse at all is a width-dependent fact, decided once in `flatten()`, not re-derived by every consumer — except for `Piece::Replaced`, which is unconditionally collapsible.** `flatten()` (`src/tui/diff_row.rs`) gains a `width: usize` parameter, used for nothing except this one measurement.

- `Piece::Replaced`: always emit `DiffRow::Purpose { piece, expanded, key }` — never `PurposeFull`. A short *new* text next to a very different *old* text is exactly the case a bare one-line excerpt would misrepresent as an ordinary edit, so the fits-check that governs `Added`/`Changed` doesn't apply here at all.
- `Piece::Added` / `Piece::Changed`: computes `available` for the purpose row (`width.saturating_sub(GUTTER_WIDTH)` minus the pillcrow prefix's own display width — the same budget the collapsed truncation itself uses, described below), right-trims the piece's current text (`Piece`'s `delta` field) of trailing whitespace, and compares its character count against that budget:
  - Fits (`trimmed.chars().count() <= available`): emit `DiffRow::PurposeFull(&'a Piece)` — renders the full trimmed text on one line with the plain `¶ ` prefix (no disclosure triangle), through the ordinary `piece_spans` + `wrap_spans` path (it fits by construction, but reusing the general path costs nothing and means a size computed slightly differently by two code paths can never disagree about whether wrapping is needed). It carries no expand state and is not in `key()`'s or `expanded()`'s match arms.
  - Doesn't fit: emit `DiffRow::Purpose { piece, expanded, key }` — collapsible, carrying a real key and expand state.

All variants are emitted (exactly one of `PurposeFull`/`Purpose`, when `diff.purpose.is_some()`) immediately after the error `Notice` rows and before the first `GroupHeading`, preceded by `DiffRow::PurposeHeading(&'a Piece)` (display-only, exactly like `GroupHeading`).

**`DiffRow::PurposeFull` is selectable despite having nothing to toggle — a deliberate, narrow exception to "only collapsible rows are selectable."** `is_selectable()` gets `| DiffRow::PurposeFull(_)` alongside `Requirement`/`Scenario`, so the cursor stops on it like any other row (useful for a consistent row-by-row scroll rhythm — the purpose row doesn't vanish from `j`/`k` traversal just because its text happens to be short). `key()` and `expanded()` are left unchanged, so `PurposeFull` falls through their `_ => None` arm. That already makes the toggle a no-op for free: `cursor_row_key_and_state` (`src/tui/app.rs:400`) does `row.key()?`, and both `toggle_cursor_row` and `set_cursor_row_expanded` bail out via that `?` before touching `self.expanded`. No new branching is needed in `App` at all — the existing generic "the row under the cursor" plumbing already produces exactly the wanted behavior once `is_selectable()` is widened. Alternative considered: skip `PurposeFull` in cursor movement (matching the "only collapsible rows are selectable" invariant literally). Rejected per direction: a purpose row that silently disappears from keyboard traversal depending on pane width or text length is a worse surprise than a selectable row whose toggle keys are inert.

**Consequence: `App` must know the right pane's current width when handling keys, not just when rendering.** `move_cursor`, `cursor_row_key_and_state` and `reset_cursor_to_first_selectable` (`src/tui/app.rs`) all call `self.diff_rows()`, which now must call `flatten(diff, &self.expanded, width)`. This mirrors the existing `right_viewport_rows` pattern exactly: add a `right_pane_width: usize` field to `App`, a `set_right_pane_width` setter called from `render_diff_tabs` alongside the existing `set_right_viewport_rows` call, and have `diff_rows()` read `self.right_pane_width` instead of taking a parameter (keeping its existing call sites unchanged). Same one-frame lag as `right_viewport_rows` already has (a key handled before the first render uses width `0`); this is accepted precedent, not a new risk category.

**The purpose heading reuses `group_heading_box`'s drawing and degrade logic, generalized to take a label string instead of computing one from `(Operation, count)`.** Extract the box-drawing into a helper that takes `(label: &str, style: Style, width: usize)`; `group_heading_box` becomes a thin wrapper that derives its label from `(op, count)` as today, and a new `purpose_heading_box(piece: &Piece, width) -> Vec<Line>` derives its label ("Added Purpose" / "Modified Purpose", no colon, matching `heading_text()`'s unpunctuated convention) and style (`added_style()` for `Piece::Added`, `modified_style()` for `Changed`/`Replaced`) from the `Piece`. `build_diff_lines` (`src/tui/mod.rs`) gets one more `if let` arm alongside its existing `GroupHeading` special case.

**The `Purpose` row's rendered content depends on its own expand state — new for this codebase.** Every existing collapsible row (`Requirement`, `Scenario`) renders identical content whether collapsed or expanded; expansion instead reveals separate child rows. The purpose row has no child row — expanding it changes what its own line(s) show. `layout::row_lines` special-cases `DiffRow::Purpose { expanded: false, .. }`, branching on the piece:
- `Piece::Added` / `Piece::Changed`: builds the row's fixed prefix (`▸ ¶ `), computes `available` the same way `flatten()` did for the fits-check (`indent = 0` — the purpose row, fitting or not, is a sibling of `Requirement`, not nested under it), and calls `truncate_chars` on the trimmed text with that budget. Since this branch is only reached when `flatten()` already determined the trimmed text doesn't fit, truncation is always genuinely happening here — no "was this actually needed" ambiguity.
- `Piece::Replaced`: renders the fixed placeholder string `"Expand to view diff"`, italicized (`modified_style().add_modifier(Modifier::ITALIC)` — modified's color, since a replacement only ever occurs for a modified purpose), through the same fits-or-truncate check as the placeholder's own text (see below), rather than through the piece's actual text at all.

`DiffRow::Purpose { expanded: true, .. }` falls through to the same `piece_spans` + `wrap_spans` path `Body`/`Intro` already use for every piece variant, so a changed purpose gets the same interleaved-runs rendering a changed intro gets, and a replaced purpose gets the same stacked before/after rendering. `DiffRow::PurposeFull` (only ever `Added`/`Changed`, per the decision above) always takes the plain full-text path, unconditionally.

**New primitive: `truncate_chars(text: &str, width: usize) -> String`.** Takes `text.chars().take(width.saturating_sub(1))`, collects, and appends `'…'` (U+2026). It lives in `layout.rs` next to `piece_spans`, since it's specific to how a piece's text is rendered, not a general wrapping concern like `wrap.rs`'s contents. It has two callers with two different fitness conventions:
- The `Added`/`Changed` collapsed branch above calls it unconditionally, because `flatten()` already guarantees truncation is necessary before this code path is ever reached.
- The `Replaced` collapsed branch measures the placeholder string itself against `available` first, and only calls `truncate_chars` if the placeholder doesn't fit — otherwise it renders the placeholder as-is, with no ellipsis. (The placeholder is 20 characters; this only matters at a pathologically narrow pane width, but it costs nothing to keep the same "only add an ellipsis when something was actually cut" rule everywhere in the row, rather than making the placeholder a special case that ignores it.)

**Gutter marker reuses existing generic machinery.** `gutter_marker` gets two more arms: `DiffRow::Purpose { piece, .. } => piece_marker(piece)` and `DiffRow::PurposeFull(piece) => piece_marker(piece)` (so an added purpose gets `+`/green, a changed or replaced one gets `~`/yellow, in either row form — identical to how an intro or scenario body already gets its marker from its own `Piece`). `key()`/`expanded()` get one more arm for `Purpose` only, mirroring `Scenario`'s. No change is needed to `App`'s toggle logic beyond the width-threading above — it already operates generically on "the row under the cursor" via `DiffRow::key()`/`expanded()`, not on a per-variant match.

## Risks / Trade-offs

- **`RowKey`'s struct→enum change touches every existing call site and test that constructs one.** Mitigation: mechanical, no behavioral change to the requirement/scenario paths; a compiler error at every site that needs updating means nothing is silently missed.
- **Whether the purpose row is `PurposeFull` or `Purpose` depends on the pane's last-rendered width, threaded through `App` a frame behind the true current width.** A resize that changes whether the purpose row fits could, in principle, be handled by a keypress before the next render updates `right_pane_width`. Mitigation: identical in kind to the existing `right_viewport_rows` lag, which the codebase already accepts; a resize event and a keypress landing in the same tick is an edge case with no visible harm (worst case, one keypress is evaluated against the pane's previous width) — and either way the row stays selectable, so there's no dropped cursor position to recover from.
- **A selectable row whose toggle keys silently do nothing is a pattern this pane uses nowhere else.** Every other selectable row (`Requirement`, `Scenario`, and `Purpose` when it doesn't fit) responds to Enter/Space/`l`/`h`. Mitigation: it's a single, narrow, intentional exception, made for cursor-traversal consistency rather than as an oversight, and it's documented as its own spec scenario ("toggling a non-collapsible purpose row has no effect") rather than left as incidental behavior.
- **Generalizing `group_heading_box` to take an arbitrary label risks disturbing the existing Requirements-heading rendering.** Mitigation: the extraction is a pure refactor (same box-drawing math, same degrade threshold check); existing `group_heading_box` tests continue to exercise the exact same output.
- **The collapsed placeholder ("Expand to view diff") is the only row content in this pane that isn't derived from the spec text being diffed.** Every other row, including every other collapsed truncation, shows real content. Mitigation: it's narrowly scoped to the one case (`Piece::Replaced`) where showing real content would actively mislead — a short excerpt of just the new text would read as an ordinary edit rather than a rewrite — and it's captured as its own spec requirement rather than folded silently into the general truncation rule.
