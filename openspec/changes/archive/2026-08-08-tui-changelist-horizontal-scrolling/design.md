## Context

See proposal.md - Why. The left pane (`src/tui/mod.rs::render_left_pane`) renders `App::rows()` (from `src/tui/row.rs::flatten`) as a ratatui `List`, which has no built-in horizontal scroll (that's a `Paragraph`-only feature via `.scroll((y, x))`). Today overflow is silently hard-clipped by ratatui with no indicator. `App` (`src/tui/app.rs`) currently holds only vertical state: `ListState` and `archived_expanded`.

## Goals / Non-Goals

**Goals:**
- Single horizontal offset in `App`, applied uniformly to every row's rendered text.
- Offset changes only in response to key handling; it is clamped against current content and pane width purely at render time, with no explicit reset path.

**Non-Goals:**
- Adjustable left/right pane split (see proposal.md - Impact).
- Per-row independent scroll or ellipsis truncation indicators (see spec: pane scrolls as a single unit, indicated by a scrollbar).

## Decisions

**Offset lives in `App`, clamped at render time, not at mutation time.** `handle_key` only increments/decrements/jumps the stored offset (saturating at 0 on the low end); it does not know the rendered pane width. `render_left_pane` computes `max_scroll = widest_row_width.saturating_sub(pane_inner_width)` from the same `Vec<Row>` and `Rect` it already has at render time, and uses `effective_offset = stored_offset.min(max_scroll)` both for slicing row text and for the `ScrollbarState`. This is what lets resize, selection change, and archived collapse/expand all self-correct through one code path instead of three separate reset rules — matches the "Horizontal scroll offset persists... clamped to current content" requirement.

Alternative considered: clamp and store the corrected value back into `App` each render (so `stored_offset` is always valid). Rejected — it entangles rendering with mutation for no behavioral difference the spec requires, and risks subtle bugs if render is ever skipped for a frame while a resize happens mid-key-sequence.

**`$`/`End` need the current `max_scroll`, which `handle_key` doesn't have — solved by caching it from the last render, not by a sentinel offset.** A naive fix would set the stored offset to a very large sentinel (e.g. `u16::MAX`) on `$`/End and let the render-time `min(stored_offset, max_scroll)` clamp pin the visible position at the right edge. That looks correct for the jump itself, but afterward `h`/left would decrement from that enormous stored value — many thousands of presses before `effective_offset` moves at all, i.e. left-scrolling would appear frozen. Instead, `App` caches the `max_scroll` computed by the most recent render (a second small field alongside the offset); `$`/`End` read that cached value directly and set the stored offset to it (a real, tight value, not a sentinel). This is safe against staleness: `event_loop` always redraws immediately before reading the next key, so the cached value is guaranteed current as of the instant before the keypress. This is different from the rejected alternative above — that one was about writing the *clamped scroll offset itself* back into `App` every render; this only caches a *derived* value (`max_scroll`) that the offset itself never depends on being pre-clamped to.

**Column offset applied by skipping characters across each row's existing styled spans — not by flattening to plain text first.** Since `List`/`ListItem` don't support horizontal scroll natively, offset must be applied directly to each row's spans: consume `offset` characters cumulatively across the row's `Span`s in order (a span's text can be partially or fully consumed), dropping characters and exhausted spans off the front, and keep every remaining fragment attached to its own span's original style. This matters concretely for archived rows, which already render as two differently-styled spans — a dimmed date `Span` and a plain name `Span`, per the existing "date is visually de-emphasized" requirement. Flattening to one plain string before slicing would discard exactly the boundary needed to know which remaining characters should stay dimmed, regressing that existing requirement the first time a user scrolls partway through an archived row. Consuming per-span, in order, preserves it for free: whatever's left of the date span (if any) is still the dimmed span, whatever's left of the name span is still the plain span. Skipping by character rather than by raw byte index remains required, not optional, for panic-safety: row text already contains multi-byte UTF-8 today (the `▸`/`▾` archived-header markers are 3-byte characters), and Rust's byte-indexed string slicing (`s[offset..]`) panics whenever `offset` doesn't land on a UTF-8 character boundary — which a naive column-as-byte-index scheme would hit almost immediately on that row.

**Widest-row measurement uses the currently visible row set** (i.e., `app.rows()` post-flatten, respecting `archived_expanded`), not some cached global maximum — consistent with "collapsing the archived section reduces the available scroll range" needing to shrink `max_scroll` without extra bookkeeping.

**Scrollbar: ratatui's `Scrollbar` widget with `ScrollbarOrientation::HorizontalBottom`, `ScrollbarState` derived from `(max_scroll, effective_offset)`.** Rendered inside the existing `Block::bordered()` along the bottom border, consistent with ratatui's typical scrollbar placement. When `max_scroll == 0` the scrollbar renders in its "nothing to scroll" state (no thumb range) rather than being conditionally omitted, keeping layout stable.

**Keybinding wiring**: extend the existing `match key.code` in `App::handle_key` with `Char('h') | Left`, `Char('l') | Right`, `Char('^') | Home`, `Char('$') | End`. No collision with existing bindings (`Up`/`k`, `Down`/`j`, `Enter`/`Space`).

**Collapsed `archived` row is underlined via `Modifier::UNDERLINED`.** Applied where the `ArchivedHeader` row's spans are built, conditioned on `!expanded`. Being a per-character style rather than a separate glyph, it survives horizontal-offset slicing for free — unlike the `▸`/`▾` marker, which is plain text at column 0 and can scroll out of view.

## Risks / Trade-offs

- [Byte-index slicing would panic on multi-byte UTF-8 content] → Resolved by design: offset is applied via `.chars().skip(offset)`, not raw byte indexing (see Decisions). Not a future concern to defer — the `▸`/`▾` archived-header markers are already multi-byte, so this must hold from the first implementation.
- [Character count vs. rendered display width can still diverge for wide/ambiguous-width characters] → Lower severity, and left open. `.chars().skip(offset)` counts *characters*, not *rendered columns*; most Unicode is 1 column per character, but some (CJK characters, some emoji, and ambiguous-width symbols — including `▸`/`▾` themselves, which fall in Unicode's East Asian "Ambiguous" width category) can render as 2 columns depending on terminal/locale. Ratatui's own text layout measures width via `unicode-width` internally, so a character-count-based offset can drift out of sync with it — e.g. `$`/End landing slightly short of or past the true rendered edge, or the scrollbar thumb not quite matching the visible edge. This is cosmetic misalignment, not a crash, and current row content (kebab-case names, ISO dates) is single-width in practice. Out of scope for now; if it matters later, compute offsets/widths with the `unicode-width` crate (matching what ratatui uses) instead of raw character counts.
- [Computing `max_scroll` from all visible rows every render is O(rows × row length)] → Negligible at this list's realistic size (dozens of changes at most); no caching needed.
