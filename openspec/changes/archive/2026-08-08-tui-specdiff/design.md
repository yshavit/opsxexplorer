## Context

See proposal.md - Why. The pieces this change assembles all exist and are unchanged by it:

- `Changes::views(&ChangeView) -> ChangeViews` (`src/changes/mod.rs:67`) resolves the live tree and the diff base for one change.
- `specs::capabilities(&ChangeViews) -> Result<Vec<String>, FsError>` (`src/specs/load.rs:17`) enumerates a change's capabilities, already sorted, already returning `Ok(vec![])` for a change with no `specs/` directory.
- `specs::load(&ChangeViews, &str) -> Result<SpecPair, SpecError>` (`src/specs/load.rs:39`) loads one capability's two sides.
- `diff::diff(&str, &SpecPair) -> CapabilityDiff` (`src/diff/mod.rs:18`) is pure, infallible at the top level, and returns `{ requirements, errors }` — errors per entry, collected.

The right pane is `render_right_pane` (`src/tui/mod.rs:86`), a bare `Block::bordered()`. `App` (`src/tui/app.rs`) holds only left-pane state and routes every key to it.

Three constraints from the layers below shape everything here:

1. **`Piece::Changed` carries two strings and byte ranges into each.** `Run::Equal { base, delta }`, `Run::Delete { base }`, `Run::Insert { delta }` — rendering one passage means interleaving slices of two different `String`s. There is no single string to style.
2. **Those offsets address `spec-model`'s normalised bodies, not the file.** `mdq` re-serialises; bullet markers, emphasis and escaping may differ from disk. The pane cannot claim to show the file verbatim, and there is no mapping back to it.
3. **`mdq` drops source positions.** `SpecError::Structure` carries a `Location { section, requirement }`, not a line number, and its `Display` impl already renders it (``under `## MODIFIED Requirements`, requirement "Change discovery"``).

## Goals / Non-Goals

**Goals:**

- One rendering path for all content, so the same text looks the same inside and outside a changed passage.
- Vertical scrolling addressed in *rendered lines*, so a requirement that wraps to eleven lines is traversable line by line.
- Wrapping that preserves per-span styling across a break, since a word-diff run can straddle one.
- Failures degrade to the smallest possible unit: a bad requirement costs a notice row, not its tab; a bad capability costs its tab, not the pane.

**Non-Goals:**

- Any parsing or diffing. `spec-model` and `spec-diff` own those and are not touched.
- Caching diffs across selections, or incremental recomputation.
- Wide-character-correct column measurement (see Risks — inherited, unchanged, from the left pane).
- Rendering `proposal.md`, `design.md` or `tasks.md`; adjustable pane split.
- **Rendering a delta's `## Purpose`.** `Delta::purpose` is parsed and carried (`src/specs/model.rs:61`), but `CapabilityDiff` does not hold it, so the pane cannot display it without also retaining the `SpecPair` alongside the diff. That plumbing is out of scope here and the pane renders no Purpose text; a new capability's tab opens directly on its requirement tree. Tracked separately.

## Decisions

**The pane is line-addressed and rendered as a `Paragraph`, not as a `List`.** This is the fork the brief flagged, and it is forced rather than preferred. `ratatui`'s `List` computes its viewport by whole items: `get_items_bounds` (`ratatui-widgets-0.3.2/src/list/rendering.rs:128`) accumulates `item.height()` and sets `state.offset` to a whole-item index. An item taller than the viewport is therefore all-or-nothing — you cannot scroll into the middle of it. That is not a cosmetic lurch, it is unreachable content: the longest line in this repo's specs is 782 characters (`openspec/specs/spec-diff/spec.md:77`), which wraps to ~11 lines at the pane's ~76-column inner width, and an expanded requirement's intro plus scenarios easily exceeds a terminal's height as a single item. The spec's "each of that row's lines can be brought into view in turn" cannot be met by `List`. So: flatten the tab to `Vec<Line<'static>>` ourselves and render `Paragraph::new(Text::from(lines)).scroll((line_offset, 0))`, which skips whole *lines* (`paragraph.rs:433`).

Alternatives considered. (a) *One `ListItem` per rendered line, keeping `List`.* Restores line-granular scrolling and free highlight, but a tree row then spans several list items, so `ListState::selected` no longer means "the selected row" — every cursor move, toggle and skip-non-selectable rule has to map an item index back to a logical row through a side table that must be rebuilt whenever the width changes. That is the same bookkeeping as the `Paragraph` approach plus a widget fighting us. (b) *`List` with `Wrap`-style items, accepting the lurch.* Rejected on the unreachable-content ground above; it is a correctness failure, not a polish one. (c) *`Paragraph` with `Wrap { trim: false }`, letting ratatui wrap.* Rejected: we need a per-row gutter column and hanging indent on continuation lines, and ratatui's wrapping has no concept of either — it would re-wrap our prefix characters into the text.

Cost, stated plainly: we give up `List`'s free `highlight_style` and its automatic scroll-into-view. Selection highlight becomes "apply `Modifier::REVERSED` to every line belonging to the selected row" — which is in fact better for a wrapped row, since `List` would highlight the whole multi-line item anyway. Scroll-into-view becomes an explicit clamp (below).

**Two stages, mirroring `row.rs`: flatten to rows, then lay rows out into lines.** `CapabilityDiff` + collapse state → `Vec<DiffRow>`; then `(DiffRow, width) → Vec<Line>`. `DiffRow` is a new type in the right pane's own module, *not* an extension of `src/tui/row.rs::Row` — the two panes share the *idea* that some rows are display-only (`is_selectable`) and nothing else; their contents have no overlap, and widening one enum to cover both would put left-pane variants in every right-pane match. The split exists so navigation logic (which rows are selectable, what the cursor moves over) is testable without a width or a terminal, matching the established pattern of unit-testing span construction and key handling directly.

`DiffRow` variants: `GroupHeading(Operation)`, `Requirement { .. }`, `Intro { .. }`, `Scenario { .. }`, `Body { .. }`, `Notice { .. }`. `is_selectable()` is true for `Requirement` and `Scenario` only — the spec's "every cursor position is one where the toggle keys do something".

**`wrap_spans(Vec<Span>, width) -> Vec<Vec<Span>>` is the one new primitive, and it breaks on word boundaries while cutting *within* spans.** A diff run is a span; a wrap point falls wherever it falls. The function walks spans in order accumulating display width, and when a break is needed splits the current span at the last word boundary at or before the limit, emitting the head with the span's own style and carrying the tail forward with the same style. A single word longer than the width is hard-broken rather than overflowing. This is the `skip_chars` (`src/tui/mod.rs:145`) idea — consume across styled spans, keep each fragment attached to its original style — turned from "drop a prefix" into "cut into rows", and it is character-based for the same panic-safety reason: byte slicing a `&str` at a non-boundary index panics, and this content is full of multi-byte characters.

Alternative considered: flatten each row to a plain `String`, wrap that, and re-apply styling by offset afterwards. Rejected for exactly the reason the left pane rejected the equivalent shortcut: flattening discards the boundaries that say which characters were an insertion, and re-deriving them from offsets means maintaining a second, parallel offset map that can drift from the first.

**Gutter and indent are a layout prefix, not part of the row's text.** Each row supplies `(marker, indent_depth)`; layout wraps the row's spans to `inner_width - gutter_width - indent`, prefixes the first line with the marker and the rest with blanks, and left-pads every line by the indent. Keeping the prefix out of the wrapped text is what makes "continuation lines start beneath the first line's text and carry no gutter marker" fall out for free rather than needing a special case, and it means a marker can never be word-wrapped away from its row.

**Markers: `+` added, `~` modified/changed, `-` removed/deleted, `»` renamed, `?` unmentioned, blank unchanged.** `»` for rename because it reads as "became", and because the other three are already spoken for by diff convention. `?` is styled dim, deliberately *not* a shade of red: unmentioned means "the delta says nothing about this", which is an authoring ambiguity, not a deletion, and colouring it like one would assert the very thing `spec-diff` refused to guess. Requirement rows take their marker from `Operation`; intro and scenario rows take theirs from their own `Piece` variant. These are different mappings on purpose — `Operation` has no unmentioned variant and `Piece` has no renamed variant, so a single shared marker function would have unreachable arms in both directions.

**An unmentioned intro gets both a marker and dimmed text.** An unmentioned intro renders the spec of record's text, which is byte-identical to what an unchanged intro renders; without a treatment the two are indistinguishable, and the intro is the one piece with no header row of its own to carry the signal. The marker alone would work in principle, but the intro sits directly under a requirement row that also has a marker, in the same gutter column, which is precisely where a reader's eye stops resolving one glyph from another. Dimming the text says "this is context recovered from the base, not something the delta asserted" at a glance. Alternative considered: dimming alone, no marker. Rejected — dim is already the styling of the `?` marker, so dim-only would make the intro's state legible only by comparison with its neighbours, and it would leave the intro the only piece in the tree whose state is not readable from the gutter.

**Word-diff spans are built by walking `runs` in order and slicing with `get()`, not `[..]`.** `Equal` slices the `delta` range (the two sides are equal by construction; picking one consistently avoids an arbitrary-looking `base`/`delta` choice per call site), `Delete` slices `base` and styles red, `Insert` slices `delta` and styles green. Ranges come from `similar` at word granularity and land on character boundaries, but they are still untrusted input from another module's arithmetic: `s.get(range)` returning `None` yields an empty span, where `&s[range]` would panic and take the whole application down mid-render. A rendering path is the wrong place to assert another module's invariants.

**Diffs are recomputed when the left-pane selection changes; layout is recomputed every render.** These are different costs and get different rules. Computing the diff means git-base resolution, file reads and markdown parsing — real I/O, and doing it per frame means doing it on every keypress including cursor movement inside the pane. So `App` recomputes `Vec<CapabilityDiff>` (plus per-capability load errors) when, and only when, the left-pane selection moves, and holds the result. Layout — flatten, wrap, offset — is pure and depends on the pane's current width, so it is redone every render exactly like `max_scroll` in the left pane, which is what lets a terminal resize self-correct with no resize handler. This is not pre-emptive caching: it is the minimum needed to keep I/O off the per-frame path, and at this repo's scale (six changes, ten spec files) even the per-selection recompute is free.

Alternative considered: recompute everything per frame, for symmetry with the left pane. Rejected — the left pane's per-frame work is arithmetic over an in-memory `Vec`; this would be `git2` history resolution plus markdown parsing, several times a second while a key is held.

**Collapse state is keyed by name, not by index, and is cleared when the selected change changes.** The expanded set holds `(capability, requirement_name, Option<scenario_name>)`. Index keys would be shorter but silently mis-target the moment the row set changes — which it does on every tab switch. Clearing on change-selection satisfies "the pane opens collapsed"; *not* clearing on tab switch means moving `]` then `[` returns to what you had, which is what a tab bar implies. Requirement names are unique within a capability's diff by construction (one entry per requirement the delta names), so the key is sound.

**Focus is a two-variant enum on `App`, with `Tab` handled before dispatch.** `handle_key` intercepts `KeyCode::Tab`, flips `focus`, and returns; otherwise it dispatches the whole `KeyEvent` to the focused pane's handler. Routing the *event*, rather than adding right-pane arms to the existing `match`, is what makes `h`/`l`/`j`/`k` mean horizontal scroll on the left and collapse/expand on the right without either handler knowing the other exists — and it is what the spec's "the other pane's state is unchanged" requires. `Ctrl+Q` stays where it is, in the event loop above `handle_key`, unaffected.

Focus is indicated by border style: the focused pane's `Block` uses a highlighted border, the unfocused pane the default. Alternative considered: emphasising the title text. Rejected — the right pane's title area is the tab bar, so title emphasis would compete with tab selection for the same visual channel.

**The tab bar is built as styled spans passed to `Block::title`, not with ratatui's `Tabs` widget.** The two are mutually exclusive: `Tabs` is a plain `Widget` rendering into a `Rect` (`ratatui-widgets-0.3.2/src/tabs.rs:369`), so it cannot draw into a block's border — it would occupy a line of the pane's interior. `Block::title` accepts anything `Into<Line>`, including `Vec<Span>` (`block.rs:366`), which is what puts the tabs *in* the top border:

```
┌ tui-changelist │ tui ────────────────────────────────┐
```

Alternative considered: the `Tabs` widget on its own line inside the block, which gives selection styling and divider handling for free. Rejected on two counts — it costs a row of the pane's height permanently, and it does not match the layout the pane was designed around. What `Tabs` provides for free is a reversed-style span for the selected tab and a separator between tabs, which is a handful of lines to build directly and leaves the border free for the pane's content.

Capabilities arrive already alphabetised from `specs::capabilities`, so tab order needs no sorting here. A one-capability change still renders the bar, for the same reason the left pane's scrollbar renders in its nothing-to-scroll state: layout that does not move as content changes. A tab bar wider than the pane is truncated by the block, which is acceptable — capability names are short and the count is small.

**Errors are rendered through the existing `Display` impls, not re-formatted.** `SpecError` and `DiffError` already produce structural, line-number-free messages naming the capability, the section and the requirement. Re-writing them in the pane would create a second wording to keep in sync with the vocabulary those modules own, and would be the likeliest place for a "line 42" to creep back in. The pane's job is placement, not phrasing:

- `capabilities()` fails → pane-level notice, no tabs (the change cannot be enumerated at all).
- `load()` fails for one capability → that tab renders a notice and nothing else; sibling tabs are unaffected, which is why `load` is called per capability rather than once for all of them.
- `CapabilityDiff::errors` is non-empty → `Notice` rows rendered above the tree, *with* the tree. Rendering the notice instead of the requirements would discard work `spec-diff` explicitly collected rather than short-circuited.
- `Changes::resolve`/`views` fails (e.g. an archived change whose base commit cannot be resolved) → pane-level notice, same as the first case.

**Scroll offset is stored and clamped at render time, following the left pane.** `App` holds a line offset and the last render's max; the render clamps `offset.min(max_line_offset)` and, additionally, adjusts the offset so the selected row's first line is visible — the one thing `Paragraph` does not do for us. `ScrollbarState` is built from the same two numbers, with `ScrollbarOrientation::VerticalRight`, using `content_length = max_offset + 1` for the reason documented at `src/tui/mod.rs:74`.

**`tui-markdown` is removed from `Cargo.toml`.** It is declared and unused (`grep -rn tui_markdown src/` finds nothing). The spec now forbids markdown rendering of diffed content, and per proposal.md that decision is uniform across changed and unchanged passages — so the dependency has no remaining use, and leaving it in place reads as a standing intention to render markdown that the spec has ruled out.

## Risks / Trade-offs

- [Character count is not rendered column width] → **Knowingly deferred, inherited unchanged.** `wrap_spans` measures in characters, as `skip_chars` does today; CJK and some symbols render two columns wide, so a wrapped line can overshoot the pane on such content. Spec text is overwhelmingly ASCII prose, and the failure is a cosmetic overhang, not a panic. The fix, if it matters later, is the same one already noted for the left pane: measure with `unicode-width`, which is what ratatui uses internally. Doing it in one pane and not the other would be worse than doing it in neither.
- [Losing `List` means re-implementing selection highlight and scroll-into-view] → **Accepted, and bounded.** Both are a few lines against a `Vec<Line>` we already build, and both are unit-testable without a terminal — unlike `List`'s behaviour, which is only observable through a rendered buffer. The alternative was unreachable content (see Decisions).
- [Wrapping the whole tab every frame is O(content × width)] → **Resolved by scale.** A capability's diff is at most a few hundred wrapped lines with everything expanded, and everything is collapsed by default. This is the same judgement the left pane made about recomputing `max_scroll` per render. If it ever bites, the fix is to wrap only the visible window, which the line-addressed model makes possible and the `List` model would not.
- [Deep nesting plus a gutter leaves little room for prose in a narrow terminal] → **Knowingly deferred.** A scenario body sits at indent 2 behind a gutter column; at 80 columns total the right pane's usable prose width is around 70, which is fine, but at very narrow widths wrapping degrades to near-vertical text. No minimum-width handling is specified. Hard-breaking over-long words means it degrades rather than clipping or panicking.
- [Collapse state is cleared on every change selection, so glancing at a neighbour and coming back loses expansions] → **Accepted deliberately.** The spec requires the pane to open collapsed; retaining per-change expansion sets would need eviction rules and would make "what state is this tab in?" depend on browsing history. Cheap to revisit later if it annoys.
- [The renamed and unmentioned paths have no real fixture in the repo] → **Mitigated by synthetic fixtures.** This change's own `tui` delta supplies MODIFIED, REMOVED **and** RENAMED against a real base spec — the first change in the repo's history to do so — so the renamed path has a genuine end-to-end case as soon as this lands. Unmentioned still has none in the repo (no delta here omits a scenario the base defines), so it is covered by hand-built `CapabilityDiff` values in unit tests, which is the right level anyway: the pane's contract is with `CapabilityDiff`, not with the filesystem.
- [`Piece::Changed` run offsets are another module's arithmetic] → **Resolved by design.** Slices go through `str::get`, so a bad range degrades to an empty span instead of panicking mid-render and taking down the terminal restore path with it.
